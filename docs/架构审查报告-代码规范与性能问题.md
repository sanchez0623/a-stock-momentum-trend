# 架构审查报告：代码规范与性能问题（优先级排序）

> 审查日期：2026-08-10
> 审查范围：`backend/`（FastAPI + SQLite）与 `frontend/`（Vite + React 18 + TS）
> 方法：源码走读 + 架构一致性比对（不涉及运行期压测）

## 总体评价

项目整体架构清晰、分层合理：数据源抽象 + 熔断降级、纯函数指标库、异步任务、统一响应包、前端 react-query + lazy 分包，作为个人交易系统工程质量明显高于平均水平。以下问题按「影响严重度 × 修复成本」排序，多数为低成本高收益项。

## P0 — 紧急（可能导致运行失败 / 数据损坏）

### P0-1 SQLite 未启用 WAL 模式与 busy_timeout（✅ 已修复 2026-08-10）

- **位置**：[db.py](backend/app/db.py) `create_engine`（未设 `PRAGMA journal_mode=WAL` / `busy_timeout`）
- **现状**：SQLite 默认 rollback journal 模式，且 busy_timeout 默认 0（遇到锁立即报 `database is locked`，不等待）。
- **风险**：盘后预热（scheduler 16:00 写 K 线缓存）与用户手动扫描、配置写入、历史落库并发发生时，读会被写阻塞、写会互斥，真实场景下会出现间歇性 `database is locked` 失败。缓存层每票 load+save 各开一次事务，放大冲突概率。
- **建议**（约 5 行改动）：engine 初始化时执行
  `PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000; PRAGMA synchronous=NORMAL;`
  WAL 下读写互不阻塞，个人单机场景收益极大。这是本次审查性价比最高的修复。
  **修复**：`@event.listens_for(engine, "connect")` 中对每个新连接执行 `journal_mode=WAL; busy_timeout=5000; synchronous=NORMAL`，已验证生效（`journal_mode=wal`），176 测试全绿。

### P0-2 批量信号评估共享同一 SQLAlchemy Session 并发执行（✅ 已修复 2026-08-10）

- **位置**：[signals.py](backend/app/api/signals.py) `_evaluate_many` → `_evaluate_one(symbol, session)`（Semaphore(5) 并发）
- **现状**：5 个协程交错使用**同一个** `Session` 做查询（`position_manager.get_position`）+ 写（`_store_signal` 读-改-写）。SQLAlchemy Session 非线程安全，identity map 与 pending 状态在并发协程中交错属于未定义行为。
- **风险**：`/signals/evaluate-batch`（持仓一键分析，最多 50 只）可能偶发对象状态错乱、重复插入或异常；难以复现、难排查。
- **建议**：`_evaluate_one` 内部改用独立短 Session（或 `db.session_scope()`），批量写入改为结果收集后一次性提交；若需保留事务一致性，可先并发只读取数、再串行落库。
  **修复**：新增 `_signal_session` 上下文管理器——单只评估复用调用方会话（兼容现有测试签名），批量评估（`evaluate_batch`）不传 session，每只票用独立短会话并在内部提交，多协程零共享。

## P1 — 高（影响性能 / 架构一致性 / 可维护性）

### P1-1 全市场扫描串行逐票取数，耗时与池规模线性（✅ 已修复 2026-08-10）

- **位置**：[engine.py](backend/app/core/screener/engine.py) `scan()` 主循环（`for i, symbol in enumerate(symbols)` + `await asyncio.sleep(0.05)`）
- **现状**：universe 默认 `"all"` 时扫描池为全市场 5000+ 只，逐票 `get_kline`（即使命中缓存也有 DB 事务开销）+ 每票强制 0.05s 降压。全市场一次扫描理论耗时 30 分钟以上量级。
- **建议**：
  1. 默认扫描池切换到 `universe`（300~800 只质量池），`all` 仅保留为显式选项；
  2. 保持对上游限流的尊重（数据源管理器已有 per-source 熔断），用 `asyncio.Semaphore(8~16)` + 动态间隔替代固定串行降压，命中缓存的票不 sleep。
  3. 扫描进度回调目前每 20 票一次，改为按百分比触发更平滑。
  **修复**：默认选股池改为上证50（sz50，配置 + 前端默认选中 + 旧库存配置迁移 all→sz50）；扫描主循环并发 3（分批 gather，每只保留 0.05s 降压）；显式传入 symbols 的列表扫描跳过预筛（显式列表优先）。

### P1-2 K 线缓存每票 3 次独立 DB 事务

- **位置**：[cache.py](backend/app/core/datasource/cache.py) `load()` / `save()` / `merge_and_save()`
- **现状**：一次 `get_kline` 未命中 = load（查询）+ merge（内存）+ save（写）≈ 3 次独立 `Session` 往返。5000 只全市场扫描 ≈ 1.5 万次事务，且每票都从 JSON 全量反序列化。
- **建议**：扫描场景改为「批量预载」：一次性 `SELECT` 出池内全部 symbol 的缓存行到内存 dict，扫描过程零 DB 读；回源成功后再批量写回（或延后到扫描结束统一写）。同时与 P0-1 的 WAL 配合，写放大问题基本消除。

### P1-3 前端自选页 N+1 实时行情请求（✅ 已修复 2026-08-10）

- **位置**：[Watchlist.tsx](frontend/src/pages/Watchlist.tsx) `WatchRow`（每个组件 `setInterval(api.quote(symbol), 10000)`）
- **现状**：N 只自选 = N 个 HTTP 请求/10s；后端明明提供批量 `get_realtime_quote` 与 `/ws/quote` WebSocket，前端未使用。页面级 `refresh` 另有 watchlist+positions+account 3 个请求/10s，共 N+3 个并发轮询。
- **建议**：自选行行情统一走**批量接口**（新增 `POST /api/quote/batch` 或复用 WS `/ws/quote`），由页面级单一定时器刷新后分发到行组件；行组件只做展示，不持有轮询。预计请求数从 N+3 → 2。
  **修复**：新增 `POST /api/quote/batch`（复用 5s 内存缓存），Watchlist 页面级单定时器批量拉取后按 symbol 分发，WatchRow 改为纯展示组件（N 请求 → 1 请求）。

### P1-4 前端状态管理双轨制（手写轮询 vs react-query）

- **位置**：全站 11 个页面中仅 [Dashboard.tsx](frontend/src/pages/Dashboard.tsx) 使用 react-query；Watchlist / Screener / Signals / AiReview / Backtest / Settings / Review / Trades / Plans 均为 `useState + useEffect + setInterval` 手写范式（[Screener.tsx](frontend/src/pages/Screener.tsx) 甚至有手写 `pollRef` 轮询任务进度）。
- **问题**：同一代码库两套数据获取范式；手写方案缺缓存/去重/卸载清理保障（Screener 已出过一次轮询泄漏相关修复），重复代码多。
- **建议**：统一迁移到 react-query（`refetchInterval` 轮询 + `staleTime` 缓存 + 全局 `retry`），尤其是 Watchlist、Screener 轮询。可分批进行，每页一个 PR。

### P1-5 前端缺少 ESLint / Prettier，CI 仅 tsc 把关

- **位置**：[package.json](frontend/package.json)（无 lint 脚本）、[ci.yml](.github/workflows/ci.yml) frontend job（仅 `npm run build`）
- **现状**：后端有 ruff + mypy + pytest 全链路，前端只有 `tsc --noEmit`（虽已开 strict/noUnusedLocals，但无风格与 hooks 规则约束）。
- **建议**：引入 `eslint`（react-hooks 插件必装，能抓到依赖数组漏项——本仓库已出现过 `useMemo` 顺序导致的真实白屏 bug）+ `prettier`，CI 增加 `npm run lint`。一行脚本级别的投入，收益立竿见影。

### P1-6 指数 K 线缓存无新鲜度检查

- **位置**：[manager.py](backend/app/core/datasource/manager.py) `get_index_kline()`（命中条件仅 `len(cached) >= count`）
- **现状**：个股 K 线有 `_cache_fresh`（日线最后日期 ≥ 今天才算新鲜），指数 K 线只判长度，收盘后缓存可能停留在前一日，导致择时闸门用陈旧指数数据。
- **建议**：复用 `_cache_fresh` 逻辑判断 `idx:` 前缀缓存；同时择时闸门扫描前拉取指数时，若缓存新鲜直接命中（现状已如此），否则强制回源。

## P2 — 中（规范 / 体验 / 安全，建议纳入迭代）

### P2-1 API 错误契约不一致，前端丢失错误详情

- **位置**：后端部分端点返回 `{code:1}` + 404 JSONResponse（[quote.py](backend/app/api/quote.py)、[signals.py](backend/app/api/signals.py)），部分 `raise HTTPException`（detail 字符串，无 code 字段）；前端 [client.ts](frontend/src/api/client.ts) `request()` 对 `!resp.ok` 直接抛 `HTTP ${status}`。
- **问题**：`HTTPException` 场景（如「任务不存在」「记录不存在」）前端只能看到 `HTTP 404`，看不到业务原因。
- **建议**：统一约定——业务错误一律 `{code: 非0, msg}` + 200，或前端解析 `body.detail` 作为 fallback msg。两端各 10 行改动。

### P2-2 CORS 全放开 + 全 API 无鉴权

- **位置**：[main.py](backend/app/main.py) `allow_origins=["*"]`；配置、持仓、AI 复盘等端点全部匿名可写。
- **现状**：注释已自述「上公网前收紧」。个人系统跑在本机/内网可接受，但一旦暴露公网，任何人都能改配置、注入伪持仓、消耗 LLM Key 配额。
- **建议**：低成本兜底——增加可选 `APP_TOKEN`（.env 配置即生效，未配置保持现状），前端在 header 附带；或部署时置于带 Basic Auth 的反代之后。

### P2-3 vite `emptyOutDir: false` 为临时 hack

- **位置**：[vite.config.ts](frontend/vite.config.ts)
- **现状**：因 WorkBuddy 安全删除保护异常改为跳过清空，构建产物可能残留旧 chunk 文件（chunk 名带 hash，会越积越多，dist 体积膨胀且可能引用混乱）。
- **建议**：恢复 `emptyOutDir: true`（或构建前手动清理 dist 目录）；若保护问题仍在，改用 `build.outDir` 指向每次全新的临时目录再替换。

### P2-4 中文配置键 + 全量 deepcopy

- **位置**：[config.py](backend/app/core/config.py)（DEFAULT_CONFIG 中文分组 key）、各模块 `cfg["趋势"]["ma_short"]` 直接取
- **问题**：键名拼错运行期才暴露；`config_manager.get()` 每次全量 deepcopy（信号引擎每次评估都调用 `_reload_cfg`）。
- **建议**：低成本——定义 TypedDict 常量组（如 `CFG_TREND = "趋势"`）；高频路径增加按路径缓存的 `get_path` 使用率（已有该方法）。完全迁移 TypedDict 成本高，不作为必做。

### P2-5 后端大量裸 `except Exception` 吞错

- **位置**：全后端（数据源层可理解，但 [engine.py](backend/app/core/screener/engine.py) 扫描循环 `logger.debug` 级别吞错）
- **问题**：扫描失败原因仅在 debug 日志，用户从界面上只能看到「某票失败被跳过」的零信息；全市场扫描时坏票原因会被淹没。
- **建议**：至少把异常摘要聚合进 `last_scan_summary`（如 top 10 失败原因统计），便于用户与 AI 复盘定位数据源问题。

### P2-6 后端任务状态均为进程内 dict

- **位置**：[backtest.py](backend/app/api/backtest.py) `_tasks`、[ai_review.py](backend/app/api/ai_review.py) `_tasks`、[screener/tasks.py](backend/app/core/screener/tasks.py)
- **现状**：重启即丢（screener 已有 history 表兜底，backtest/ai_review 无）。注释已承认 MVP 取舍。
- **建议**：不阻塞。若要做，优先把 backtest 策略回测结果落库（结果大、计算贵，丢了最可惜）；可仿照 ScreenerHistory 加一张表。

### P2-7 前端 API 类型与后端手工双维护

- **位置**：[client.ts](frontend/src/api/client.ts)（632 行，类型 + 函数混排）
- **问题**：后端改字段后前端类型静默漂移（代码里已有「旧任务结果可能缺失，前端需容错」的补丁式注释）。文件已偏大。
- **建议**：低风险改进——把类型定义拆到 `src/api/types.ts`；运行时校验可后续引入 zod（对个人项目优先级不高）。

### P2-8 测试缺口：前端零单测、CI 不跑 mypy

- **现状**：后端 21 个测试文件覆盖核心逻辑，良好；但 CI（[ci.yml](.github/workflows/ci.yml)）未跑 `mypy`（本地 Makefile 有 lint 含 mypy），前端无任何测试。
- **建议**：CI 补 `mypy app`（几十秒成本）；前端暂不强制单测，但 `src/utils/` 纯函数（格式化、颜色）可低成本补 vitest。

## 建议执行顺序（快速见效）

1. **P0-1 SQLite WAL**（30 分钟）：稳定性立竿见影，零风险。
2. **P1-3 自选行情批量接口**（半天）：请求数 N+3 → 2，前端观感明显。
3. **P2-1 错误契约统一**（半天）：前后端各小改，排查问题体验提升。
4. **P1-1 + P1-2 扫描并发 + 缓存批量预载**（1~2 天）：全市场扫描时间从小时级降到分钟级，注意保持对上游限流的尊重。
5. **P1-5 前端 ESLint**（半天）：先上 `react-hooks` 规则，能防住已出现过的白屏类回归。
6. **P1-4 轮询迁移 react-query**（分批 1~2 周）：Watchlist → Screener → 其余，每页独立提交。
7. **P0-2 批量评估 Session 隔离**（半天）：并发正确性兜底。
8. 其余按迭代节奏消化，P2-2 鉴权建议在「上公网」之前完成。
