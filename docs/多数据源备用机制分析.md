# 多数据源备用（fallback）机制分析

> 分析对象：`backend/app/core/datasource/`（含 `base.py` / `manager.py` / 5 个源实现）
> 对照依据：`个人动量趋势交易系统-设计方案.md` §3.1–§3.4
> 日期：2026-08-08

---

## 一、结论先行（直接回答你的两个问题）

**Q1：多数据源备用的逻辑目前是怎么样的？**
业务只依赖单例 `DataSourceManager`，不直接碰任何上游 SDK。取数时按 **「近期偏好 + 配置优先级」** 顺序依次尝试各源，**首个成功即返回**（failover）。旁路有：每源健康分/熔断、60s 探活、成功后置顶、K线/行情缓存降级。

**Q2：每个接口会有不同的备用吗？**
**默认情况下不会按接口各配一套备用源。** 基础四件套（K线 / 实时价 / 股票列表 / 探活）共用**同一个全局尝试顺序** `_active_order()`。
但系统里**确实存在「按能力分源」的第二套路由**（见 §三），只对「可选能力」（指数成分股 / 行业 / 基本面 / 业绩 / 指数线）生效——这些接口会只路由到声明了该能力的源。
而你举例里感知到的「选股备用少、持仓备用多」，**真实来源是「各源实现的方法不同」+「业务层自己的兜底」**，并不是"每个接口各配了 A/B/C、B/D/E"。

> 一句话：**目前没有"每个接口各自指定备用源集合"的配置；"差异化备用"是能力声明 + 方法实现差异自然形成的，不是显式按接口配置的。**

## 二、当前机制全貌

### 核心数据结构
- 5 个已注册源（见 `build_sources()`，优先级顺序）：
  `mootdx → tencent → baostock → eastmoney → akshare`
  - 默认 `enabled` 全为 `True`（config.py）。
- 每个源实现统一接口 `DataSourceInterface`：`get_kline / get_realtime_quote / get_stock_list / health_check` + 一组「可选能力」方法。
- 每个源有两个关键声明：
  - `supports_realtime: bool`（盘后型源置 False，不参与实时行情）
  - `supports: tuple`（声明自己提供哪些可选能力）
  - `supports_period(period)`：是否支持某周期（baostock 无分钟线）

### 取数流程（三层防御）
1. **缓存优先**：K线走 SQLite `kline_store`，实时价走内存 LRU（TTL 5s）。
2. **回源 failover**：按 `_active_order()` 顺序逐个试，首个成功即返回；熔断中的源跳过。
3. **缓存降级**：回源全失败 → K线降级返回旧缓存；实时价只返回缓存命中的部分。

### 熔断 / 健康
- 每源 `HealthState`：连续失败次数、平均延迟、熔断截止时间。
- 连续失败 **5 次**（代码里把方案原定的 3 改成了 5，理由是腾讯偶发抖动易误熔断）→ 熔断 600s。
- 成功后把该源置顶到「近期偏好」（`_bump_preference`），实现软负载均衡 + 自愈。

## 三、两套路由：全局顺序 vs 能力分源（关键）

| 路由方式 | 适用接口 | 是否"按接口不同备用" | 实现 |
|---|---|---|---|
| **全局顺序 failover** | K线 / 实时价 / 股票列表 | 否（三者共用同一顺序） | `get_kline` / `get_realtime_quote` / `get_stock_list` |
| **能力路由** (`_try_capability`) | 指数成分股 / 行业 / 基本面 / 业绩 / 指数线 | **是**（只路由到声明该能力的源） | `get_index_constituents` / `get_industry_map` / `get_fundamentals` / `get_earnings_events` / `get_index_kline` |

全局顺序的"自然差异化"来自两处过滤（不是按接口配置）：
- `get_realtime_quote`：跳过 `supports_realtime=False` 的源（baostock 盘后型被跳过）。
- `get_kline`：跳过 `supports_period(period)` 为 False 的源（baostock 的分钟线被跳过，日/周线可用）。
- `get_stock_list`：会**跳过未实现全量列表的源**（mootdx / tencent 抛 `NotImplementedError` → `except NotImplementedError: continue`，不计入失败/熔断，`_bump_preference` 成功置顶）；**baostock / eastmoney / akshare 三个真正实现了它**，所以"股票列表"实际有 **3 个真备用**（优先级顺序 mootdx→tencent→baostock→eastmoney→akshare，前两个快速跳过、由 baostock 顶上）。

能力路由示例：`get_index_kline`（择时闸门用指数线）= **东财优先 → 其次任何声明 `index_kline` 能力的源（baostock，自动做 secid→代码转换）**，全部失败才返回 None。**所以它并不是"只绑东财"**，而是东财 + baostock 双候选。

## 四、用你的两个例子对号入座

### 例 1：选股取科创板（你预期 A/B/C 三种方式）
实际代码里**没有 A/B/C 三套并存取数**。真实路径是：

1. **业务级三级兜底**（`StockScreener._resolve_symbols`）：
   - ① 本地 `stocks` 表缓存（最优先，不依赖任何在线源）
   - ② 在线 `get_stock_list(market)` → 走 manager 全局 failover
   - ③ 在线全失败 → 降级为「自选 + 持仓」池
2. **`get_stock_list` 的备用源**：**baostock、eastmoney、akshare 三个都真正实现它**（baostock 的 `get_stock_list` 调 `query_all_stock`，排在东财之前；mootdx/tencent 抛 NotImplementedError 被跳过）→ 实际有 **3 个真备用**，优先级顺序里 baostock 通常先顶上。
3. 拿到全量列表后，用代码前缀 **688 / 689** 过滤出科创板——这是"过滤"，不是"另一种取数方式"。
4. 对每只候选股再 `get_kline` → 这次是 **5 个源全都能 failover**（分钟线 baostock 被自动跳过）。

→ 你以为的 A/B/C，其实是「**本地缓存 / 在线列表(baostock·东财·akshare 三源) / 自选持仓兜底**」这三层业务兜底。而"取科创板列表"本身的备用是 **3 个源（baostock→eastmoney→akshare）**。

### 例 2：持仓实时价刷新（你预期 B/D/E 方式）
- `GET /api/positions` → `get_realtime_quote(symbols)` → manager 全局 failover。
- 5 个源里 **baostock 因 `supports_realtime=False` 被跳过**，所以实际是 **mootdx / tencent / eastmoney / akshare 共 4 个真备用**。
- 外加 quote_cache 5s LRU：命中直接返回，不打源。
- 全部失败/未命中时，只返回缓存里有的部分，**没有"第二套指定源集合"**。

→ 你以为的 B/D/E，实际是「**5s 缓存 / 全局 4 源 failover**」两层。它比选股列表的备用多，纯粹因为"实时价这个方法 mootdx/tencent/akshare 都实现，而股票列表只有东财/akshare 实现"。

## 五、与方案（§3）对照：按方案做是否更健壮？

**先澄清一个关键误解：方案本身设计的就是「一个全局优先级队列 + 健康分 + 熔断」，并没有"每个接口各配一套备用源"的设想。** 所以你脑中的 A/B/C、B/D/E 是你自己的扩展设想，不是方案原文。

方案 vs 现状对比：

| 方案要求（§3.2/§3.3） | 现状 | 是否达标 |
|---|---|---|
| 全局优先级队列 + 健康分 + 探活 | ✅ 已实现 | 达标 |
| 熔断：连续 3 次 → 10 分钟 | ⚠️ 代码改成 **5 次**（防腾讯误熔断），仍为 10 分钟 | 偏宽松，更稳但更"忍" |
| 东财风控专项（降频/串行/退避/UA+NID/代理） | ✅ eastmoney_src 已实现 | 达标 |
| 缓存层（K线 SQLite + 行情 LRU 5s） | ✅ 已实现 | 达标 |
| "关键业务绝不只绑东财" | ✅ 指数线东财+baostock 双候选；**分类刷新已接入 manager 熔断/健康**（熔断则跳过、成败回报熔断） | 达标 |
| 盘后批量预热 | ✅ `scheduler._after_close_warmup` 已接入真实逻辑（预热自选股+持仓股日线 K 线入缓存） | 达标 |

### 直接回答"按方案来是不是更健壮"
- **不会更健壮于"全局 failover"本身**——因为现状已经就是方案那套全局 failover，不存在"照方案做就能多出一套按接口备用"的事。
- **真正"不够健壮"的地方不在 failover 拓扑，而在这几个具体缺口**（均已修复，见 §六）：
  1. ✅ `get_stock_list` 的跨方法误熔断（NotImplementedError 跳过）。
  2. ✅ 分类映射刷新（`classification.refresh_classification`）接入 manager 熔断/健康 + 失败安全。
  3. ✅ 盘后预热已接入真实逻辑（自选股+持仓股日线 K 线预热入缓存）。
- 另外，你说的"按接口指定 A/B/C 备用"属于**架构增强**，不是方案要求。它有用处（比如实时价优先腾讯、列表优先东财），但全局 failover + 健康自愈已经能自适应选最优源，静态指定反而可能降低自愈能力。**建议先补 §六 的真实缺口，再决定是否做按接口指定源。**

### 关于"每个接口不同备用"该不该做
- 方案已通过 **`supports` 能力路由** 提供了"按能力分源"的框架（目前只用于可选能力：行业/基本面/业绩/指数成分/指数线）。
- 如果你想要"K线优先 mootdx、实时价优先 tencent"这类**基础四件套的按接口偏好**，可以在 manager 里给每个方法加可选 `preferred` 参数，或在 config 里加"方法→优先级"维度。这是增量增强，不是必须。

## 六、现状里发现的健壮性缺口（可优先修）

- **✅ BUG-1（跨方法误熔断风险）— 已修复（2026-08-08）**：原 `get_stock_list` 未过滤能力，mootdx/tencent 抛 `NotImplementedError` 被 `except Exception` 计入失败，可能污染其 K线/实时价熔断。现为 `except NotImplementedError: continue`（与 `_try_capability`/`_fetch_kline` 一致），并补 `_bump_preference` 成功置顶。详见 `manager.py` `get_stock_list`。
- **✅ BUG-2（单点绑定）— 已修复（2026-08-08）**：原 `classification.refresh_classification` 直连 akshare，绕过 manager 熔断。现：① manager 新增 `source_circuit_open`/`report_source` 公共方法；② 刷新前若 akshare 熔断则跳过；③ 成败回报 manager 熔断（分类失败也计入 akshare 连续失败）；④ 失败安全——拉取为空但库中有数据时保留上次有效数据、显式报错，不静默清空。说明：分类数据（申万/板块）是 akshare 生态专属，manager 的 `get_industry_map` 口径不同（证监会行业），故采用"接入熔断+失败安全"而非硬塞第二源。
- **✅ 缺口-3（预热占位）— 已修复（2026-08-08）**：`scheduler._after_close_warmup` 已接入真实逻辑——读取自选股+持仓股符号（`Watchlist`∪`Position`），逐个经 `data_source_manager.get_kline` 预拉日线 K 线入缓存（沿用 failover+缓存）。详见 `scheduler.py`。
- **小瑕疵**：`HealthState.record` 里 `self.last_success_time = latency_ms`（把延迟当时间存了），注释也写了"实际用当前时间"但没改。不影响 failover，但状态展示的 `last_success_time` 不准。
- **已具备的健壮性增强（顺带一提）**：`setup()` 里有 `_heal_priority()`——已注册但不在 `priority` 配置里的源（例如后加的 baostock）会自动补到队尾，避免"注册了却永远轮不到"的 orphan 问题；这是比方案更周到的自愈。另外 baostock 是**可选依赖**，需 `pip install baostock` 才真正生效，未安装时 `setup()` 会捕获 `RuntimeError` 并跳过它，不影响其余 4 源。

## 七、一句话总结
> 现有系统 = **一个全局 failover 队列（5 源）+ 一套"按能力分源"的可选路由 + 缓存降级**。它没有"每个接口各配一套备用源"的配置，你感知的差异来自"各源实现的方法不同 + 业务层兜底"。照方案做**不会**自动多出按接口的备用集（因为方案本就不是这么设计的）；当前真正该补的是 §六 的三个缺口，而不是去加一套按接口的静态备用。
